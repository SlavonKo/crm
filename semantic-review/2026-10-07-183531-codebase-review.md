я# MotoWorkshop CRM — Orders & AI feature review

This is a new Angular 22 CRM for a motorcycle workshop, built around signals, standalone components, and a Groq-backed AI assistant. The main concerns cluster around: API key exposure on the client, a doubled import, `any`-casts in the form layer that undercut the typed form interface, inconsistent language across the UI, and a `manual:` prefix pattern that will produce orphaned records once Firestore lands.

**Watch for:**
- **confirmed** — Groq API key is sent in every browser request (`Authorization` header constructed in `AiService`). There is no server-side proxy.
- **confirmed** — `toSignal` / `takeUntilDestroyed` are imported twice from the same module in `order-edit.ts`.
- **confirmed** — `inventoryItemId` is silently mirrored from `sku` in `#buildPartUsedGroup`, making the field always wrong.
- **confirmed** — `filterNormHours` is called on every keystroke inside `@for`, creating O(n²) per-frame work as labor rows grow.
- **confirmed** — The template mixes Ukrainian, Russian, and English across hardcoded strings and `transloco` keys in the same file.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The store layer (`OrdersStore`, `ClientsStore`) is clean signal-first code with a clear separation between writable state and derived `computed()` values. The `DynamicFormService` successfully bridges strongly-typed reactive forms with the AI draft flow, but a single line in `#buildPartUsedGroup` silently copies `sku` into `inventoryItemId`, so every part added to an order will carry a wrong inventory reference when the Firestore backend lands.

The `AiService` sends the Groq API key directly from the Angular app in the `Authorization` header. Every user who opens DevTools can read it. This is the single highest-priority issue before any production deployment.

The `order-edit` component manages two parallel form modes (select-from-DB vs manual entry). When the manual-client path is taken, `onSave()` writes `"manual:Іван Іваненко"` into `clientId`, a field typed as a document reference. All downstream reference lookups—in `OrdersList`, `OrderDetail`—fall back to "Loading..." permanently. This is silent until real data flows.

The `filterNormHours` method is called inline inside a `@for` loop, re-executing for every labor row on every change detection cycle.

The UI language policy is undefined. Hardcoded Ukrainian in `order-edit.html`, hardcoded English in `order-detail.html`, and `transloco` keys used for everything else coexist in the same feature. The infrastructure is already wired; the hardcoded strings need to route through it.

### Groq API key in the browser bundle

`AiService#callGroq` builds the `Authorization` header from `this.#config.groqApiKey`, which is read from `import.meta.env['NG_APP_GROQ_API_KEY']`. Angular resolves this at build time and inlines the value into the JavaScript bundle. Anyone who opens the Network tab or inspects the bundle can read the key and make Groq calls at the app's expense.

The fix is a thin server-side proxy (a Vercel/Cloudflare function, a Firebase Cloud Function, or any Node server) that holds the key and forwards validated requests to Groq. The Angular side sends the user's prompt and context; the server applies input limits and injects the key server-side. This also gives a place to add per-user rate limiting and audit logging.

### `inventoryItemId` always set to `sku`

```typescript
#buildPartUsedGroup(defaults?: Partial<AiWorkOrderDraft['partsUsed'][0]>): FormGroup<PartUsedForm> {
  return new FormGroup<PartUsedForm>({
    inventoryItemId: new FormControl(defaults?.sku ?? '', { nonNullable: true }),  // ← bug
    sku:             new FormControl(defaults?.sku  ?? '', { nonNullable: true }),
```

`AiWorkOrderDraft` parts have no `inventoryItemId`—they only carry `sku`. That's correct, because AI-generated parts aren't matched to inventory records yet. But the form field `inventoryItemId` should default to `''` (unlinked), not to the SKU string. When `formToOrderPayload` serialises the form and this reaches Firestore, every AI-drafted part will have an `inventoryItemId` that looks like a valid reference but contains a SKU string.

### `manual:` prefix clientId/motorcycleId

When a user creates an order with a manually-entered client, `onSave()` writes:

```typescript
this.form.get('clientId')?.setValue(`manual:${label}`, { emitEvent: false });
```

`WorkOrder.clientId` is typed as a document reference. Storing `"manual:Іван Іваненко"` there makes all reference lookups in `OrdersList.getClientName()` and `OrderDetail.client()` fall back to "Loading..." permanently. The UI currently hides this because the manual label is displayed elsewhere, but once real data flows, these orders become orphaned and unsearchable.

Two viable fixes: add a `manualClientLabel?: string` field to `WorkOrder` so the string is stored in a semantically correct place; or, on save, call `ClientsStore.create()` to produce a real `Client` record and store its generated `id` in `clientId`. The second approach means manual and DB clients are treated identically by all downstream code.

### `filterNormHours` in a `@for` loop

The template calls `filterNormHours(item.get('description')?.value)` inside `@for (item of laborItems.controls; track $index)`. Angular's change detection invokes this on every cycle, for every row. At 5–10 labor rows with a dataset of ~40 entries the cost is negligible, but the pattern doesn't scale and contradicts the signal-first approach used everywhere else in the component.

The standard fix: pre-compute a `Map<rowIndex, NormHourEntry[]>` signal that updates when the labor form array or a description field changes, and let the template read from it.

### `any` casts undercutting typed forms

```typescript
readonly liveSubtotalLabor = computed(() => {
  const items: any[] = (this.#mainFormValues()['laborItems'] as any[]) ?? [];
  return items.reduce((s, i) => s + (+(i.hours ?? 0)) * (+(i.ratePerHour ?? 0)), 0);
});
```

`#mainFormValues` carries a snapshot whose `laborItems` field is `Array<{ description: string; hours: number; ratePerHour: number; ... }>`. The `as any[]` cast makes TypeScript blind to field name changes. If `ratePerHour` is ever renamed, this silently returns `NaN`. Casting to the concrete snapshot type preserves safety at no runtime cost.

### Duplicated badge/label logic

`getBadgeClass(status)` and `getStatusLabel(status)` are copy-pasted verbatim between `OrderDetail` and `OrdersList`. `statusOptions` is also independently constructed in both components from the same `ORDER_STATUS_LABELS` source. A shared `OrderStatusPipe` or a free function exported from `order-status.enum.ts` would make future status additions a single-point change.

### Admin phone numbers in source

```typescript
const ADMIN_PHONES: Record<string, { displayName: string; uid: string }> = {
  '+380675609143': { displayName: 'Адмін 1', uid: 'admin-uid-1' },
  '+380934072482': { displayName: 'Адмін 2', uid: 'admin-uid-2' },
};
```

Real phone numbers in source control. The `.env.local.example` pattern already exists in the repo; add `NG_APP_ADMIN_PHONES` there and read it in `AuthService` the same way `ConfigService` reads the Groq key.

### i18n inconsistency

Three layers of language coexist in the order feature:
- Ukrainian hardcoded in `order-edit.html`: "Клієнт", "Вручну", "З бази", "Мотоцикл", "Держ. номер", "Дати", and a dozen more.
- English hardcoded in `order-detail.html`: all section headers ("Work Breakdown", "Labor Items", "Parts Used") and table column labels.
- `transloco` keys used for everything else.

The `en.json` and `ua.json` files already have keys for most of these strings. The hardcoded labels need to route through `| transloco`.

One extra oddity: `order-detail.html` contains a stray CSS class comment `ARROW-BACK` and `LIST` on two elements — likely copy-paste artifacts that should be removed.
